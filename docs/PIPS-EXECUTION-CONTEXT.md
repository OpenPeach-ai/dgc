# Reviewed execution context and main-chat evidence

API 9 and registry schema 8 add explicit promotion of a completed, accepted Patch
or Pulse outcome into Workspace Context. The record is a historical runner receipt,
not a current health assertion, model-generated fact or permission grant.

Standalone Pulse plan receipts (API 21) are readable historical command evidence
but are not eligible for this outcome acceptance/context promotion flow. See
[PIPS_PULSE_PLANS.md](PIPS_PULSE_PLANS.md).

## Review contract

`accept_pip_execution_context` takes `workspace_id`, `run_id`, `expected_revision`
(the workspace context revision) and `expected_review_revision` (the currently
accepted execution-outcome revision). It returns `{context}`. The local controller
supplies the recording actor. It accepts no custom receipt, source revision,
summary, artifact path, command or output text.

The controller authorizes workspace membership before decoding evidence, validates
the immutable execution result and its handoff/input lineage, and checks the latest
accepted review against the supplied revision. Context revision and outcome review
are checked under the same write transaction as the append and activity event.
Stale, reopened, dismissed, cross-workspace, malformed and oversized sources fail
without creating a record. There can be only one active receipt per workspace/run.
Archive it explicitly before recording a later review.

The entry has `kind: execution`, `classification: runner_receipt`, and
`verification: recorded_execution_only`. It stores run/Pip IDs, model, job version,
committed source, complete-result SHA-256, accepted review revision, private changed
file count, patch hash/size, optional Patch-input receipt, and at most four command
status/exit/output-hash receipts. Exact argv and output text stay in the original
run; the context holds a digest of each canonical argv/cwd pair. Counts and titles
are generated by the controller. No model summary is promoted as verified text.

The existing context budgets apply: 32 active entries, 512 retained entries,
6 KiB per entry and 16 KiB for the complete pinned snapshot. A later outcome review
never rewrites a historical receipt or already-queued run. Its text explicitly says
later reviews may differ and the receipt grants no authority. Accepting a review
of failed tests preserves the failures; it cannot convert them into passing tests.

Schema 8 adds the execution kind to the context table, retains all existing active
and archived records, and adds active-run uniqueness. The table rebuild and schema
version change share one transaction; failure restores the old table and version.

CLI:

```sh
dgc pips context accept-execution RUN_ID --workspace WORKSPACE_ID \
  --expected-revision CONTEXT_REVISION --expected-review-revision REVIEW_REVISION
```

The shared extension/Remote client presents a separate confirmation from the
execution review itself. Recording an outcome does not apply a patch or queue work.

## Main-chat access

`pips_context` now supports `action: execution` with `run_id`, `offset` and `limit`
(maximum three commands per page). It is restricted to the current chat workspace.
The response distinguishes model interpretation from historical runner evidence,
includes current outcome-review disposition, and pages exact recorded commands,
status, exit codes and artifact hashes. Known credentials are redacted. Optional
summary/path/output previews may be omitted to stay within the 24 KiB response
budget; explicit truncation flags remain, while argv and evidence digests are
preserved. An artifact reference does not provide arbitrary filesystem access.

Pip listings now distinguish audit, conversation, patch, test and draft runs from
their bounded manifest instead of calling every non-conversation an audit.

## Independent-runner policy boundary

Raw headless `pips_control`, `pips_enable` and `pips_runtime` commands refuse any
active `DGC_SESSION_POLICY` (including malformed policies) or requested sandbox.
A separate Pip worker cannot inherit a foreground session's limited filesystem or
permission scope. This check runs before queueing and again before execution;
using the raw wire below the SDK cannot bypass it. The refusal preserves request
correlation. Ordinary unrestricted local editor controllers retain their controls.
The same guard hides and refuses `pips_context` and `pips_propose` in restricted
model sessions: cached independent-run evidence may contain source outside a
foreground path policy, even though the tool itself is read-only.

Python and TypeScript SDK access is documented in the SDK Pips guide. It requires
explicit inherited local state with no RuntimePolicy/sandbox; isolated sessions
remain restricted. SDK mutations additionally require per-call host approval.
